## Authentication, identity, ownership, and permissions

Keep these concepts distinct:

1. **RepoMedic authentication:** Frontend uses Clerk (`frontend/src/lib/auth/clerk-adapter.tsx`, `frontend/src/lib/auth/clerk-token.ts`); authenticated API calls carry a Clerk bearer token. Server pages use Clerk `auth.protect()`. Backend `get_current_user` resolves the RepoMedic user. A Clerk user ID/display name is not a GitHub login.
2. **GitHub user identity:** During a new personal GitHub App installation, `backend/app/services/github_connection_service.py` compares the installation account's GitHub numeric ID with a verified GitHub external account linked to that Clerk user. The frontend bridge does not expose that external identity or GitHub OAuth token. The persisted `GitHubConnection.account_login` and `account_type` describe the App installation account; an organization login is not the signed-in human contributor.
3. **Installation ownership/scope:** A `GitHubConnection` belongs to a RepoMedic user (`user_id`) and has an installation ID. Repositories belong to that connection. Repository endpoints call `get_repository_or_404` for RepoMedic ownership, then `GitHubAppClient` uses a short-lived **installation access token**. The token represents the GitHub App installation and its granted repository permissions; it is not a user token and must not be used as proof of which human authored contributions.
4. **Organization installations:** Current new-installation verifier accepts only `account.type == "User"` with a verified linked GitHub external account; it explicitly says new organization connections need verified organization authorization. Do not assume an org installation login identifies an individual or silently broaden ownership policy.

Current installation permission validation in `backend/app/services/github_connection_service.py` requires `issues: write`, `pull_requests: read`, `contents: read`, `actions: read`, `administration: read`, and `vulnerability_alerts: read`. This is an installation-time gate for the saved connection, not a guarantee that every repository endpoint succeeds forever. UI must keep permission/auth errors distinct from empty data. Current GitHub client authenticates repository calls with the installation token (`backend/app/integrations/github/client.py`); there is no GitHub user-token client.

Both metadata reads support GitHub App installation access tokens. No grant, installation, ownership policy, or token strategy was changed.

### Exact data semantics

- **Language footprint is PRIMARY-language distribution.** Its denominator `N` is the full connected repository collection, deduplicated by repository ID, independent of repository search and metadata success. Each repository contributes exactly once. A named primary language contributes one repository to that language; an explicit GitHub `language: null` contributes to **No primary language**; missing/invalid/failed/pending metadata contributes to **Unknown**. Null is classified only when metadata was successfully read; failed metadata never becomes confirmed no-language.
- Every footprint row and stacked segment uses `repository count / N * 100`, including no-primary-language and unknown groups. Known groups are never renormalized over the successfully fetched subset. Percentages display one decimal place, so displayed rounded totals may differ slightly from 100%; bar widths use unrounded percentages. The same color helper drives bar segments, primary-language dots, and legend dots. The icon and actual connected-repository count are always separate from metadata coverage.
- **Coverage** means confirmed primary-language status (named or explicitly none) over all connected repositories. The card labels partial coverage while any repository is pending, missing, malformed, or failed, including an all-unknown collection. It shows complete primary-language coverage when all statuses are confirmed, even if some separate byte reads failed. Loading discovery does not invent a count; discovery failure reports count unavailable; an actually empty connected collection shows 0 with no percentage bar. Search filters cards but never changes the footprint denominator.
- **Card language distributions use code bytes per repository**, from the full unpaginated languages object. They are separately labeled `Code languages · by bytes`; each percentage is language bytes divided by that repository's total reported language bytes. They are not primary-language repository counts or human contribution shares. An available empty/zero-byte object shows `No language bytes reported`; a failed/invalid map shows `Language bytes unavailable`. The adapter rejects any unexpected `rel="next"` continuation rather than claiming a first response is complete. Primary-language status is not inferred from byte shares.
- **Counters:** stars and forks come from `stargazers_count` and `forks_count`. GitHub's REST `open_issues_count` is returned as `open_issues_and_pull_requests` and labeled **Open issues + PRs**. It is an open combined counter, not an issues-only count, PR-only count, or all-time total. No separate issue/PR counts are fabricated. Missing/invalid counters show unavailable; a real numeric zero displays 0.
- Cards retain owner/name, visibility, branch, native accessible selection and blue active styling, and add a two-line truncated description, all available topics, primary-language dot, counters, GitHub repository `updated_at` time, byte distribution, and metadata observation time. GitHub's repository update time is labeled Updated; it is not presented as the latest commit time. The API's primary-language null does not claim that the repository contains no files or no byte data.

### Requests, cache, and failure isolation

The server bounds active metadata snapshots to four per event loop/process. Each snapshot performs its two upstream reads sequentially, uses the existing HTTP timeout, and has a 25-second active-read timeout (queue waiting is separate). Duplicate in-flight reads share a task; cancelling one waiter does not cancel another's shared read. Cache keys include user, repository, connection, installation, GitHub repository ID, and saved name. Returned cached objects are copied. Cache capacity is 256 snapshots, with 60-second successful coverage and 15-second partial/failed coverage TTLs. Database authorization always precedes lookup. HTTP responses explicitly use `Cache-Control: private, no-store`.

The browser loader is scoped to the mounted workspace, not a global provider or persistent cross-account store. It deduplicates queued/in-flight/cached requests, bounds executions to four across scope changes, skips queued work that has left the repository scope, caps cached entries at 512, and uses 60/15-second success/partial TTLs. Refresh repositories invalidates settled browser entries; server TTLs still apply. Returning to the window revalidates the connected repository set, and expired metadata is re-read on subsequent loads. Neither layer polls; cached snapshots are not guaranteed real-time. Pending metadata, a single failed repository, or a byte-only failure cannot block selection or another repository's metadata. Superseded hook results cannot replace the current collection.
